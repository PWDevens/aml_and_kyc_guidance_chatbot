## 6. Edge cases & guard rails

- **Do not corrupt `data/`.** Two prior incidents (progress.md). For AC-5's from-scratch
  rebuild, prefer scratch `CHROMA_PATH`/`FAQ_DB_PATH`/`ANSWER_CACHE_PATH` overrides, or
  snapshot `data/` first and restore. Any test/script that writes must isolate ALL config
  paths (progress.md "General observations": use a single `_tmp_cfg`-style helper setting
  every derived path). New AC-2 tests MUST follow this — a new test that writes to the
  real `data/faq.db`/`cache.db`/`chroma` is a defect.
- **Fresh-venv AC-1** must be a *genuinely fresh* venv (new dir), not the current one, or
  the "clean install" claim is hollow. Use the scratchpad dir for the venv if needed.
  Some heavy deps (torch/sentence-transformers/chromadb/onnxruntime-genai) are large —
  the install may take minutes; that is expected, not a failure. If a transitive dep
  can't resolve from the freeze, that's a real finding to fix in the lock, not to hide.
- **Latency AC-3** — the FIRST FAQ/generation request in a process pays model-load cost
  (embedder + reranker are `lru_cache`-lazy per iter-1 debt). Measure p50 over a few
  warm requests OR clearly label cold-vs-warm; a cold first-request number mislabeled as
  steady-state is misleading. Report method.
- **Disclaimer-in-SSE note (do NOT expand scope, just record):** PRD §5/§7 require the
  compliance disclaimer in *every API/SSE response payload*; it currently lives only in
  the UI footer (`index.html:73`), not in the SSE stream. This is a pre-existing
  PRD-conformance gap, NOT introduced here. **Decision: record it as a finding in
  `changes.md` / progress.md and (optionally, if trivial and low-risk) add a one-line
  `disclaimer` field to the `done`/`citations` SSE event** — but if adding it risks any
  test churn or behavior surprise, leave it as a documented follow-up rather than force a
  backend change in the final hardening pass. Do not let this balloon into a feature.
- **Dockerfile index strategy:** since the index is gitignored/not committed, the
  Dockerfile must either (a) run `build_index` + `seed_faq` as a build/entrypoint step
  (slower image build, self-contained) or (b) expect the built `data/` mounted as a
  volume (compose `volumes:`). Pick one, make it internally consistent with the compose
  file and the README run instructions, and document the choice. Either is defensible;
  inconsistency between Dockerfile/compose/README is the failure mode to avoid.
- **`onnxruntime-genai` pin:** progress.md documents 0.14.1 working (API drift from
  0.5.2). Pin to whatever `pip freeze` reports as installed — that is the proven-working
  version. Do not pin to a version the env doesn't actually have.

## 7. Patterns to follow

- **Config:** env-driven `RagConfig` dataclass (`src/rag/config.py`), `_b()` for bools,
  `os.getenv(name, default)`. No config framework. Any new knob follows this exactly.
- **Tests:** stdlib + pytest, tempdir isolation of every DB path a test touches (shared
  `_tmp_cfg`-style helper preferred), no new test framework/plugin, network-tolerant live
  tests use `pytest.skip` on failure (see `test_etl_fedreg_live.py`). New tests exercise
  real code paths (the gate rejects tautologies).
- **Scripts:** `python -m scripts.<name>` module invocation, `argparse`/`sys.argv` flags
  as `eval.py` does; print human-readable summaries.
- **Docs:** README/CHANGELOG voice already established — match the existing tone and the
